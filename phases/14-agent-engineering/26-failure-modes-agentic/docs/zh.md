# 失败模式：智能体为什么会坏

> 中文译文。代码、命令和标识符保持英文。若与原文不一致，以同目录 docs/en.md 为准。

> MASFT（Berkeley，2025）在 3 个类别里编目了 14 种多智能体失败模式。Microsoft 的 Taxonomy 记录了现有 AI 失败如何在智能体环境中被放大。行业现场数据收敛到五种反复出现的模式：幻觉动作、范围蔓延、级联错误、上下文丢失、工具误用。

**Type:** 理解 + 动手做
**Languages:** Python（标准库）
**Prerequisites:** 第 14 阶段 · 05（Self-Refine 与 CRITIC），第 14 阶段 · 24（可观测性）
**Time:** ~60 分钟

## 学习目标

- 说出 MASFT 的三个失败类别，以及每一类里至少四种具体模式。
- 解释为什么智能体式失败会放大已有的 AI 失败模式（偏见、幻觉）。
- 描述行业里反复出现的五种模式及其缓解办法。
- 实现一个标准库检测器，用失败模式标签标注智能体轨迹。

## 问题

团队交付的智能体在 90% 的轨迹上能工作。那 10% 的失败不是随机噪声——它们落进少数反复出现的类别。一旦你能叫出它们的名字，你就能监控它们并修好它们。

## 概念

### MASFT（Berkeley，arXiv:2503.13657）

Multi-Agent System Failure Taxonomy。14 种失败模式聚成 3 个类别。标注者之间的 Cohen's Kappa 为 0.88——这些类别可以可靠地区分。

核心主张：失败是多智能体系统里根本性的设计缺陷，不是靠更好的基座模型就能修好的 LLM 局限。

### Microsoft Taxonomy of Failure Mode in Agentic AI Systems

- 现有的 AI 失败（偏见、幻觉、数据泄露）在智能体环境中被放大。
- 新的失败从自主性中浮现：规模上的非意图动作、工具误用、任务漂移。
- 这份白皮书是智能体产品的风险登记册。

### Characterizing Faults in Agentic AI（arXiv:2603.06847）

- 失败来自编排、内部状态演化和与环境的交互。
- 不只是「坏代码」或「坏的模型输出」。

### LLM Agent Hallucinations Survey（arXiv:2509.18970）

两种主要表现：

1. **指令遵循偏离（Instruction-following Deviation）**——智能体不遵循系统提示词。
2. **长程上下文误用（Long-range Contextual Misuse）**——智能体忘记或误用更早轮次的上下文。

子意图错误：遗漏（漏掉步骤）、冗余（重复步骤）、错序（步骤顺序不对）。

### 行业里反复出现的五种模式

Arize、Galileo、NimbleBrain 在 2024–2026 年的现场分析收敛到：

1. **幻觉动作。** 智能体调用一个不存在的工具，或编造参数。
2. **范围蔓延。** 智能体把任务扩展到用户所求之外（多开 PR、多发邮件）。
3. **级联错误。** 一次错误调用触发下游效果。一次幻影 SKU 幻觉触发四次 API 调用——一起多系统事故。
4. **上下文丢失。** 长程任务忘记早期轮次的约束。
5. **工具误用。** 用错误的参数调用正确的工具，或者整个调用了错误的工具。

级联是杀手。智能体分不清「我失败了」和「任务不可能」，还经常在 400 错误上幻觉出一条成功消息来闭合循环。

### 缓解：每一步都设闸门

在推理链的每一步放自动核实闸门，对照环境状态检查事实依据。具体来说：

- 按步的安全分类器（第 21 课）。
- 工具调用的参数校验（第 06 课）。
- 把检索到的内容与已知事实交叉核对（第 05 课，CRITIC）。
- 通过重新探测状态来检测成功幻觉（文件真的创建了吗？）。

### 失败监控会在哪里出错

- **只标注崩溃。** 大多数智能体失败产出的是看起来合法的输出。需要内容级检查。
- **没有基线。** 漂移检测需要一个最近已知良好的状态；没有它，你就不能说「这在变差」。
- **告警过多。** 每一次失败都发一页。要聚类并限流。

## 动手做

`code/main.py` 实现一个标准库失败模式标注器：

- 一份覆盖五种模式的合成轨迹数据集。
- 每种模式的检测函数（工具调用、输出、重复动作上的签名模式）。
- 一个标注器，给每条轨迹打标签，并报告模式分布。

运行：

```
python3 code/main.py
```

输出：每条轨迹的标签加上聚合分布，廉价地复现 Phoenix 的轨迹聚类所呈现的东西。

## 使用

- **Phoenix** 用于生产漂移聚类（第 24 课）。
- **Langfuse** 用于会话重放加标注。
- **自定义** 用于你的可观测性平台检测不到的领域专有签名。

## 交付

`outputs/skill-failure-detector.md` 生成针对你的领域定制的失败模式检测器，并接到一个轨迹存储上。

## 练习

1. 为「成功幻觉」增加一个检测器：智能体返回成功，但目标状态没有改变。
2. 给你做过的一个产品的 100 条真实轨迹打标签。哪种模式占主导？修好它的成本是什么？
3. 实现一个「级联半径」度量：给定第 N 步的一次失败，它影响了多少下游步骤？
4. 阅读 MASFT 的 14 种失败模式。挑三种适用于你的产品的。写检测器。
5. 把一个检测器接进 CI 作业：如果有 ≥5% 的轨迹被标上某种模式，就让构建失败。

## 关键术语

| 术语 | 人们怎么说 | 它实际的意思 |
|------|----------------|------------------------|
| MASFT | 「多智能体失败分类法」 | Berkeley 的 14 种模式分类 |
| 级联错误 | 「涟漪失败」 | 一次早期错误沿 N 步传播 |
| 上下文丢失 | 「忘了约束」 | 长程轮次丢掉早期轮次的事实 |
| 工具误用 | 「错误的工具 / 错误的参数」 | 调用合法，调用方式错误 |
| 成功幻觉 | 「伪造的完成」 | 智能体在 400 上声称成功；状态未变 |
| 范围蔓延 | 「越界」 | 智能体做了比所求更多的事 |
| 指令遵循偏离 | 「不服从」 | 忽略系统提示词或用户约束 |
| 子意图错误 | 「计划缺陷」 | 计划执行中的遗漏、冗余、错序 |
