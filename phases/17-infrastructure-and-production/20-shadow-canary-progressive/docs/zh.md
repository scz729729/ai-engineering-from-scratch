# LLM 的影子流量、金丝雀发布与渐进式部署

> 中文译文。代码、命令和标识符保持英文。若与原文不一致，以同目录 docs/en.md 为准。

> LLM 发布把软件部署里最难的部分叠在一起：没有单元测试、失败模式是弥散的、信号来得晚。顺序是（1）影子模式 — 把生产请求复制给候选模型，记录、比较，对用户零影响；能抓住明显的分布问题，但不是质量保证；（2）金丝雀发布 — 渐进式流量转移 10% → 25% → 50% → 75% → 100%，每一步都有门禁；跟踪延迟百分位、每请求成本、错误/拒绝率、输出长度分布、用户反馈率；（3）稳定性确认之后，对截然不同的备选方案做 A/B 测试。非确定性不可消除 — 由于 GPU 浮点非结合性加上批大小方差，相同输入在不同运行之间的准确率变化最高可达 15%。成本是变量，不是常量 — 一个好 20% 的模型，每次调用可能贵 3 倍。回滚速度具有决定性：如果回滚还得重新部署，你就太慢了。策略住在配置/标志里；模型住在带固定摘要的注册表里；回滚 = 翻转策略 + 把阈值改回去 + 在数秒内固定旧模型。

**Type:** 理解
**Languages:** Python（标准库，玩具级金丝雀推进模拟器）
**Prerequisites:** Phase 17 · 13（可观测性）、Phase 17 · 21（A/B 测试）
**Time:** ~60 分钟

## 学习目标

- 区分影子模式（零影响比较）、金丝雀（实时流量的渐进式暴露）和 A/B（稳定性已确认之后的比较）。
- 列举五项 LLM 特有的金丝雀指标（延迟、每请求成本、错误/拒绝、输出长度分布、用户反馈）。
- 解释为什么 LLM 的非确定性（最高 15%）改变了发布里「稳定」的含义。
- 设计一条以秒计（策略翻转）而不是以小时计（重新部署）的回滚路径。

## 问题

你发出一个新模型。离线评测显示准确率提升 3%。你在生产里把它打开。24 小时之内，成本上升 40%，用户点踩上升 8%，三张客户工单说「回答很怪」。你回滚。重新部署要 3 小时。周末毁了。

这里面每一环都可以避免。影子模式本可以在任何用户看到之前抓住那 40% 的成本尖峰。金丝雀本可以在点踩一动时停在 10%。策略标志回滚本可以只要 30 秒。这门纪律填的，就是「离线评测看起来不错」和「真实用户满意」之间的缺口。

## 概念

### 影子模式

候选收到和生产相同的请求；输出被记下来，不返回给用户。对用户零影响。要记的是：

- 输出内容（相对生产的差异）。
- token 计数（成本差值）。
- 延迟。
- 拒绝和错误。

能抓住的：成本失控、长度回退、明显的拒绝变化、硬错误。抓不住的：用户会感知到的质量差。影子是冒烟测试，不是质量测试。

### 金丝雀发布

带门禁的渐进式流量转移。典型推进：1% → 10% → 25% → 50% → 75% → 100%。每一步对 5 项指标设门禁：

1. **延迟百分位** — P50、P95、P99。违规：金丝雀的 P99 > 基线的 1.5 倍。
2. **每请求成本** — 混合后的美元成本。违规：高于基线 20% 以上。
3. **错误 / 拒绝率** — 5xx 加上显式拒绝。违规：基线的 2 倍。
4. **输出长度分布** — 均值 + P99。违规：分布发生偏移。
5. **用户反馈率** — 点踩 / 工单提交。违规：基线的 1.5 倍。

### 非确定性是新的方差

相同的输入会产出不相同的输出。原因：

- GPU 浮点非结合性（浮点归约的顺序随批次变化）。
- 批大小方差（同一条提示词处在 128 的批次里，和处在 16 的批次里不一样）。
- 采样（temperature > 0）。

实测：在相同的评测集上，各次运行之间的准确率变化最高可达 15%。发布里的「稳定」是指指标落在预期方差之内，不是和基线逐项相同。把门禁设在噪声底之上。

### 成本是变量

一个好 20% 的模型，每次调用可能贵上 3 倍。每请求成本是五项门禁之一。发出一个「更好」、却把单位经济打破的模型，就是该回滚的情形。

### 回滚才是武器

- 策略标志（功能标志系统）：在配置里翻转百分比；只要数秒。
- 模型固定（注册表摘要）：已固定的模型不会自动升级。
- 回滚 = 把标志改回去 + 把已固定摘要设成上一个。数秒，不是数小时。

如果你的栈必须重新部署才能回滚，先把这个修好再发。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进式交付控制器。与 Istio/Linkerd 的加权路由集成。

**Istio 加权路由** — 服务网格这一层的流量拆分。

**KServe / Seldon Core** — 带内置金丝雀的模型服务。

**功能标志** — LaunchDarkly、Flagsmith、Unleash。策略级翻转，不用重新部署。

### 指标节奏

金丝雀门禁每 5–15 分钟查一次，取决于流量大小。1% 的流量、每分钟 10 个请求，每个窗口给出 50–150 个数据点 — 对延迟够用，对用户反馈噪声很大。10% 大约会给出 10 倍。推进应当在每一步停够久，让这一步攒够样本。

### A/B 这一步是可选的

如果新模型截然不同（不同的行为、不同的成本曲线、不同的语气），金丝雀通过之后以 50% 对它做 A/B 测试。如果它只是一个改进版本，金丝雀门禁一过就直接到 100%。

### 你该记住的数字

- 金丝雀推进：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：相同输入上，运行之间的方差最高可达 15%。
- 五项金丝雀指标：延迟、成本、错误/拒绝、输出长度、用户反馈。
- 成本门禁：高于基线 20% 以上即为违规。
- 回滚：数秒，不是数小时。

## 练习

1. 运行 `code/main.py`。注入 25% 的成本回归。金丝雀在哪一阶段停下？
2. 你的新模型离线准确率提升 3%，但每请求成本是 +18%。能发吗？取决于策略 — 两条路径都写出来。
3. 设计一条端到端不到 60 秒的回滚。列出所需的基础设施。
4. 非确定性在你的评测上显示 ±7%。把金丝雀门禁设成不会误报。你用哪些倍数？
5. 影子模式在进入金丝雀之前抓住了 40% 的成本尖峰。写出在影子里触发的告警规则。

## 关键术语

| 术语 | 人们怎么说 | 它实际的意思 |
|------|----------------|------------------------|
| 影子模式 | 「复制到新的」 | 零影响地发给候选，只为了记录 |
| 金丝雀 | 「渐进式流量」 | 带门禁、暴露给用户的渐进发布 |
| 门禁 | 「发布检查」 | 阻止继续推进的指标阈值 |
| 非确定性 | 「LLM 方差」 | 不可消除的逐次运行差异 |
| 策略标志 | 「翻转标志即可回滚」 | 配置级回滚，以秒计而不是以小时计 |
| 模型固定 | 「注册表摘要」 | 对某个模型版本的不可变引用 |
| Argo Rollouts | 「K8s 渐进式」 | Kubernetes 原生的金丝雀/回滚控制器 |
| KServe | 「推理 K8s」 | 带金丝雀原语的模型服务 |
| Istio 加权 | 「网格拆分」 | 服务网格的流量拆分器 |
