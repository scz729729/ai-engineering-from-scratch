# LLM 的 FinOps — 单位经济与多租户归因

> 中文译文。代码、命令和标识符保持英文。若与原文不一致，以同目录 docs/en.md 为准。

> 传统 FinOps 在 LLM 支出上会坏掉。成本是 token 交易，不是资源开机时间。标签对不上 — 一次 API 调用是一笔交易，不是一项资产。工程决策（提示词设计、上下文窗口、输出长度）就是财务决策。2026 手册有三个要在第一天就做插桩的归因维度：按用户（`user_id`）用于席位定价和扩张，按任务（`task_id` + `route`）用于产品表面成本和优先级，按租户（`tenant_id`）用于单位经济和续约。四层 token — 提示词、工具、记忆、响应 — 一个桶会藏住支出。多租户产品的执行阶梯：按租户的速率限制（预期峰值的 2–3 倍，清晰的 429 + retry-after）；每日支出上限（合同天花板的 1.5–3 倍；触发收紧速率 + 告警）；支出 z-score > 4 时的终止开关（自动暂停 + 呼叫值班）。归因模式：打标签再聚合、遥测连接器（trace ID → 账单；准确率最高）、采样再外推、基于模型的分摊、事件溯源、实时流式。单位指标：每次已解决查询的成本、每个生成产物的成本 — 不是 $/M token。事后打标签总会漏；在请求创建时做插桩。

**Type:** 理解
**Languages:** Python（标准库，带终止开关的玩具成本归因模拟器）
**Prerequisites:** Phase 17 · 13（可观测性）、Phase 17 · 14（缓存）
**Time:** ~60 分钟

## 学习目标

- 解释为什么传统 FinOps（标签 + 层级）在 LLM 支出上会坏掉，并说出三个新的归因维度。
- 枚举四层 token（提示词、工具、记忆、响应），以及为什么单桶计费会藏住成本。
- 为一个多租户产品设计执行阶梯（速率 → 支出上限 → 终止开关）。
- 选择一个单位指标（每次已解决查询 / 产物的成本），而不是 $/M token。

## 问题

你的账单写着 $40,000。你不知道：
- 哪个租户花的。
- 哪个产品功能驱动的。
- 是否有单个用户在滥用。
- 罪魁是提示词膨胀、工具调用，还是记忆放大。

在提供方侧打标签再聚合，对云资源（EC2、S3）有效，因为标签会传播到行项目。LLM API 调用不会自动打标签 — 你必须在调用点盖上用户/任务/租户，并一路带着。事后归因总会漏掉边界情况。

## 概念

### 三个归因维度

**按用户**（`user_id`）：谁在花什么。驱动席位定价、扩张对话，识别高用量用户。

**按任务**（`task_id` + `route`）：哪个产品表面花什么。驱动功能优先级、砍掉昂贵功能的决策。

**按租户**（`tenant_id`）：哪个客户是盈利的。驱动单位经济、续约定价、层级阈值。

第一天就在调用点对三者全部做插桩。事后永远更差。

### 四层 token

| 层 | 例子 | 占总量的典型百分比 |
|-------|---------|---------------------|
| 提示词 | 系统 + 用户输入 | 40–60% |
| 工具 | 回喂的工具调用结果 | 20–40%（智能体工作负载） |
| 记忆 | 先前对话 / 检索到的文档 | 10–30% |
| 响应 | 模型输出 | 10–30% |

把四层装进一个桶会让优化失明。在你的归因 schema 里把它们拆开。

### 执行阶梯

1. **速率限制**，按租户。预期峰值的 2–3 倍。返回带 `Retry-After` 的 429。租户感到摩擦；没有意外账单。

2. **每日支出上限**，按租户。合同天花板的 1.5–3 倍。触发：收紧速率限制 + 告警客户成功。

3. **终止开关**，当支出相对租户基线的 z-score > 4。自动暂停租户；呼叫值班；升级到运维 + 客户成功。

### 归因模式

- **打标签再聚合**：盖上元数据头；稍后聚合。简单；粗糙。
- **遥测连接器**：通过 trace ID 把追踪连到账单。准确率最高。成熟团队做的事。
- **采样 + 外推**：采样 5–10%，再乘。对粗略支出划算；会漏掉尾部。
- **基于模型的分摊**：用回归推断成本驱动因素。用于没有标签的历史数据。
- **事件溯源**：成本作为流中的事件（Kafka / Kinesis）。实时。
- **实时流式**：仪表板亚秒更新。

### 单位指标是每 X 的成本

$/M token 是厂商的说法。产品指标：

- 每张已解决支持工单的成本。
- 每篇生成文章的成本。
- 每个成功智能体任务的成本。
- 每个用户会话分钟的成本。

把成本绑到一个产品结果上。否则优化没有锚点。

### 成本归因追踪的形状

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每一次调用都发出。存在数据湖里。按维度聚合。Phase 17 · 13 的可观测性栈就是它的栖身之处。

### 叠加节省栈

栈：缓存 + 批处理 + 路由 + 网关。四者齐全时：
- 缓存 L2（Phase 17 · 14）：输入便宜约 10 倍。
- 批处理（Phase 17 · 15）：打五折。
- 路由到便宜模型（Phase 17 · 16）：成本降低 60%。
- 网关效率（Phase 17 · 19）：冗余 + 重试。

最好情况下叠加后约为朴素基线的 5–10%。大多数团队用上了 2–3 个杠杆；很少有人把四个都叠上。

### 你应该记住的数字

- 归因维度：按用户、按任务、按租户。
- 四层 token：提示词、工具、记忆、响应。
- 终止开关：支出 z-score > 4。
- 单位指标：每次已解决查询的成本，不是 $/M token。
- 叠加优化：有可能约为基线的 5–10%。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|----------------|------------------------|
| 按用户归因 | “用户级成本” | 每一次调用都盖上 `user_id` |
| 按任务归因 | “功能成本” | `task_id` + `route` 标识产品表面 |
| 按租户归因 | “客户成本” | `tenant_id`；驱动单位经济 |
| 四层 token | “成本层” | 提示词 + 工具 + 记忆 + 响应 |
| 速率限制 | “429 护栏” | 在网关强制的按租户天花板 |
| 每日支出上限 | “每日天花板” | 以租户为范围、带告警的预算 |
| 终止开关 | “自动暂停” | 支出 z-score > 4 触发自动暂停 |
| 每次已解决的成本 | “产品单位指标” | 成本绑到产品结果，而不是 token |
| 遥测连接器 | “追踪到账单” | 准确率最高的归因模式 |
| 叠加优化 | “缓存+批处理+路由+网关” | 复合节省到基线的约 5–10% |
