# MCP 可靠性、取消与流控

> 中文译文。代码、命令和标识符保持英文。若与原文不一致，以同目录 docs/en.md 为准。

> 请求 ID 把一条消息关联起来。它不会让副作用变得安全，不会停掉工作者，也不会保护流免受慢消费者的影响。

**Type:** 动手做
**Languages:** Python
**Prerequisites:** 第 13 阶段，第 09、13 课
**Time:** ~120 分钟

## 学习目标

- 为 stdio 和 Streamable HTTP 实现正确的取消信号。
- 解决完成与取消的竞态，取消之后不再发送消息。
- 把请求取消和持久的 `tasks/cancel` 语义分开。
- 根据副作用和显式幂等键做重试决策。
- 限制进度队列的上界，同时保留最终响应。
- 通过重连、重新拉取和带抖动的退避恢复流。

## 问题

快乐路径藏着最贵的分布式系统缺陷。

客户端调用一个工具。服务器开始工作。进度到达。代理缓冲了这条流。客户端到达超时并断开。服务器在一毫秒之后完成。客户端用一个新的 JSON-RPC id 重试。变更执行了两次。

每个组件在本地都行为正确。系统在全局上失败了。

MCP（模型上下文协议）定义了消息和传输行为，但你的应用仍然拥有：

- 时间预算；
- 业务幂等；
- 有界队列；
- 重试分类；
- 持久任务状态；
- 重连和重新拉取策略。

本课把这些决策做进一个确定性模拟器。没有 sleep、没有套接字、也没有随机失败。你直接控制取消事件的顺序。有一个同步线程测试，迫使两个账本客户端争夺同一个幂等键。

## 请求取消取决于传输

意图在每种传输上都一样：客户端不再需要一个尚在途中的结果。线上的信号不同。

### stdio

stdio 使用一条共享的双向通道。客户端发送一条通知：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

这条通知是发出即忘。服务器不对它发出 JSON-RPC 响应。

服务器应当停止工作、释放资源，并避免为已取消的请求发送响应。当请求未知、已经完成，或无法安全停止时，它可以忽略取消。

畸形的、未知的、以及已经完成的取消通知都会被忽略。把这些竞态变成新的错误，只会制造更多竞态。

### Streamable HTTP

现代的 Streamable HTTP 让每个请求拥有自己的 HTTP 响应或 SSE 响应流。客户端通过关闭该请求的响应流来取消。

不要为一次普通的 HTTP 请求 POST `notifications/cancelled`。流关闭才是取消信号。

服务器一旦观察到断开，就应当停止工作，并且不得再为该请求发送更多消息。

### 服务器发出的取消范围很窄

服务器不用 `notifications/cancelled` 去取消任意的客户端调用。在 stdio 上，服务器发出的取消保留给终止 `subscriptions/listen` 请求。把这条路径和普通的客户端请求取消分开。

## 取消是一场竞态

两种事件顺序都合法。

### 取消获胜

```text
request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response
```

### 完成获胜

```text
request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification
```

客户端也必须忽略它已经放弃的请求上迟到的响应。网络延迟意味着任何一方都无法证明对方先观察到了哪一个事件。

```figure
mcp-reliability-race
```

本课的 `RequestCoordinator` 只存储一个终态。取消之后 `complete()` 不返回响应。迟到的取消不能改变一条已完成的记录。

## 超时需要两只时钟

单靠一个空闲计时器不够。

使用两个限制：

1. **空闲超时。** 请求可以多久不产生有用活动。
2. **最大超时。** 从请求开始起的绝对墙上时钟预算。

进度可以重置空闲时钟。它绝不能取消最大截止时间。

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

在 1500 ms 时，请求仍然活跃，因为最新的进度只有 300 ms 老。在 2000 ms 时，最大截止时间会取消它，即使另一条进度事件在 1999 ms 到达。

进度是可选的。服务器可以接受一个进度令牌，却不发出任何更新。绝不要把令牌的存在变成无限超时。

MCP 的进度值必须递增。完成或取消之后，通知停止。对进度做速率限制，这样快的工作者就不能淹没传输。

## 请求取消不是 `tasks/cancel`

这两种机制解决的是不同的生命周期。

| 机制 | 目标 | 信号 | 成功意味着什么 |
|-----------|--------|--------|--------------------|
| stdio 上的请求取消 | 一个在途 RPC | `notifications/cancelled` | 客户端放弃了该请求；服务器应在可行时停止 |
| HTTP 上的请求取消 | 一条在途响应流 | 关闭该流 | 客户端放弃了该请求；服务器应在可行时停止 |
| `tasks/cancel` | 一个持久 Task | 普通的 MCP 请求 | 服务器已确认取消意图 |

一次成功的 `tasks/cancel` 结果并不能证明工作者已经停止。任务可能保持 `working`，直到某个工作者检查点观察到这个标志。工作可能在那个检查点之前就完成。

不要在 HTTP 连接关闭时擦掉持久任务状态。创建 Task 的理由，就是它的生命周期比一次请求、一条连接更长。

## 新的 JSON-RPC ID 不是幂等

JSON-RPC id 关联请求和响应。它们不标识一次业务操作。

假设客户端用 id `41` 提交一笔扣款，丢失了响应，再用 id `42` 重试。服务器看到两条不同的消息。没有应用层的键，它无法知道它们代表同一次结账。

幂等键标识业务意图：

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

服务器存储：

- 这个键；
- 操作参数的指纹；
- 已提交的结果。

相同的键和相同的参数返回已存储的结果。相同的键配上不同的参数则被拒绝。这可以防止意外复用键去变更另一项业务操作。

### 账本边界必须原子且持久

下面这个顺序是不安全的：

```text
check key
run mutation
store result
```

两个工作者都可能观察到键不存在，并都去执行变更。效果已经发生、存储尚未完成时崩溃，会在重试时制造同样的歧义。

本课使用文件支撑的 SQLite 账本。`BEGIN IMMEDIATE` 把键检查、模拟的业务效果、执行计数器和已存储结果串行化进同一个事务。两条独立的账本连接用同一个键竞速，因此只会观察到一份已提交的结果和一次执行。关闭再重新打开账本，这条记录仍然在。

每个返回值都从已存储的 JSON 重建。调用方永远拿不到账本持有的可变对象，所以修改返回的字典不会破坏以后的重放结果。

模拟器的业务效果，是同一个 SQLite 事务里的回执和执行计数器。真正的支付、部署或外部 API 调用，并不会因为写了一张本地表就变成原子的。生产环境需要一个持久的共享数据库事务、一个事务性 outbox，或一个强制同一幂等键的上游提供方。单靠进程锁保护不了多个副本，也熬不过重启。

### 重试矩阵

实现重试之前先分类。

| 类别 | 例子 | 重试规则 |
|------|---------|------------|
| 安全 | 没有副作用的确定性读取 | 在理解失败边界之后，用新的 JSON-RPC id 重试 |
| 有条件 | 带持久幂等键的变更 | 用同一个键和完全相同的参数重试 |
| 不安全 | 没有业务去重的变更 | 不要自动重试；先对账 |

`readOnlyHint` 和 `idempotentHint` 这类工具注解仍然是不可信的提示。应用契约和服务器实现才决定重试是否安全。

## 背压是正确性的一部分

SSE 生产者生成进度的速度，可以快过客户端、代理或网络的消费速度。无界队列会把缓慢变成内存耗尽。

使用有界队列，并定义什么可以丢失。

进度是可替换的。对同一个令牌，较新的进度值取代较早的值。最终的 JSON-RPC 响应不可替换。

本课的缓冲区采用这条策略：

1. 合并同一令牌上相邻的进度。
2. 容量到达时丢掉最旧的进度。
3. 把流标记为需要权威的重新拉取。
4. 保留最终响应。
5. 拒绝这样一种状态：为了保留最终响应，必须丢掉另一个最终响应。

这是带显式恢复的有界丢失。静默丢失不是策略。

### 代理缓冲

服务器可以正确地流式发送，而反向代理把事件扣在缓冲区里。

对于 SSE 响应，发送：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 年的 Streamable HTTP 规范建议 `X-Accel-Buffering: no`，以便兼容的代理立即投递事件。

对于安静的长寿命流，定期发出一条 SSE 注释：

```text
:
```

客户端忽略注释行。中间人看到流量，就不太会关闭一条空闲连接。

保活不是进度。不要仅仅因为一条传输注释到达，就重置操作在语义上的空闲超时。

## 重连意味着重新拉取

现代的 Streamable HTTP 不支持通过 `Last-Event-ID` 做可恢复的 SSE。

`subscriptions/listen` 流断开之后：

1. 用一个新的 JSON-RPC id 打开一次新的监听请求。
2. 恢复想要的订阅过滤器。
3. 用权威方法重新拉取受影响的工具、资源、提示词或 Task。
4. 按稳定标识符对应用状态去重。
5. 不要仅仅因为响应丢失，就重放一次不安全的变更。

示例恢复计划明确把 `sendLastEventId` 设为 false，并列出要重新拉取的资源。

### 防止重连羊群

如果 10,000 个客户端在恰好一秒时同时重连，正在恢复的服务器会再次失败。

使用带抖动和上限的指数退避。本课用客户端 id 和尝试次数计算确定性抖动，以便测试可复现：

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

生产环境可以使用密码学安全的随机数，或运行时随机数。不变量是分布，不是某个具体公式。

## 动手做

`code/main.py` 构建五个小的可靠性组件。

### `RequestCoordinator`

- 以空闲截止时间和最大截止时间启动一个在途请求；
- 发出单调的进度通知；
- 产生正确的 stdio 或 HTTP 取消信号；
- 忽略无效的取消通知；
- 把取消与完成的终态竞态显式化；
- 把服务器发出的取消保留给 stdio 订阅。

### `MutationLedger`

- 证明没有业务键时，两个 JSON-RPC id 会执行两次；
- 用文件支撑的 SQLite 事务完成键检查、模拟效果、执行计数器和结果提交；
- 在独立的账本连接之间，用一个幂等键对匹配的参数去重；
- 拒绝把一个键配上不同参数复用；
- 返回防御性副本，并在重新打开后保留已提交的记录。

### `DurableTaskService`

- 确认一次取消请求；
- 让任务保持 `working`，直到某个工作者检查点；
- 说明为什么确认不等于最终状态。

### `BoundedSseBuffer`

- 在压力下合并或丢弃进度；
- 记录需要权威的重新拉取；
- 永不丢弃最终响应。

### 恢复辅助函数

- 返回对代理安全的 SSE 头和保活注释；
- 创建一份重连和重新拉取计划；
- 用确定性的指数退避和抖动摊开重试。

## 使用

在仓库根目录：

```bash
cd phases/13-tools-and-protocols/29-mcp-reliability-cancellation-and-flow-control/code
python3 main.py
python3 -m unittest discover tests -v
```

演示会跑中央竞态的两侧，在一个临时的文件账本里执行事务性去重的变更，让一个有界进度缓冲区过载，并展示一个持久 Task 从已确认的取消走到工作者观察到的取消。

## 交互实验

不加 sleep，跑四种事件顺序。

1. 启动请求 `A`，取消它，然后调用 `complete()`。
2. 启动请求 `B`，完成它，然后投递取消。
3. 启动请求 `C`，在每个空闲截止时间之前发出进度，然后越过最大截止时间。
4. 在 Streamable HTTP 上启动请求 `D`，并关闭它的响应流。

为每个场景记录：

- 请求的终态；
- 是否存在最终响应；
- 放到线上的取消信号；
- 客户端应当忽略哪一个事件。

然后把 `D` 改成 stdio。操作相同，但取消信号必须改变。

## 练习实验

给 `MutationLedger` 增加一个 `reserve_inventory` 变更。

要求：

1. 键绑定 SKU、数量、租户和操作名。
2. 用相同的键和相同的参数重试，返回第一次预留。
3. 数量改变后再重试会失败，并且不会再做一次预留。
4. 已经提交但丢失了响应的执行，可以按键对账。
5. 结果不记录秘密或支付数据。
6. 客户端没有提供键时，禁用自动重试。
7. 增加一次模拟的订阅断开，并在决定下一步之前重新拉取库存记录。
8. 在一个屏障上启动两条账本连接，并发提交同一个键。断言只提交了一份预留。
9. 修改第一次返回的预留对象。重放该键，证明存储的结果没有改变。
10. 关闭并重新打开账本文件，然后按键对账这份预留。

让实验保持诚实：如果库存住在另一个服务里，说明那个服务是否接受同一个幂等键，或者是否由事务性 outbox 把本地提交桥接到远程效果。

`outputs/skill-mcp-reliability-reviewer.md` 是一份扁平的可靠性审查技能。把一次 MCP 操作、传输、超时策略、重试行为、队列策略和恢复计划交给它。它返回竞态表、重试分类、幂等边界、流控检查和失败夹具。

## 验证

当下列陈述为真时，本课才算完成：

- stdio 取消发送 `notifications/cancelled`，并且收不到响应。
- Streamable HTTP 取消关闭请求流，并且不发送取消 POST。
- 先取消后完成会抑制最终响应。
- 先完成后取消会保留响应，并忽略迟到的取消。
- 进度可以重置空闲超时，但永远不能重置最大超时。
- 仅有一个新的 JSON-RPC id 会再次执行变更。
- 一个幂等键加上完全相同的参数，在两条连接并发竞速时只执行一次。
- 已提交的记录在重新打开后仍然存在，重放返回防御性副本。
- 修改一份返回的结果不能改变已存储的结果。
- 有界缓冲区保持在容量之内，并保留最终响应。
- 重连使用新请求，不发送 `Last-Event-ID`，并重新拉取受影响的状态。
- `tasks/cancel` 的确认让任务保持非终态，直到工作者观察到它。

## 生产失败模式

| 失败 | 可观察症状 | 正确应对 |
|---------|--------------------|------------------|
| HTTP 客户端 POST 取消通知 | 服务器和客户端对请求寿命意见不一致 | 关闭该请求的 SSE 响应流 |
| 服务器在接受取消之后仍响应 | 客户端收到一个无法使用的迟到结果 | 当取消获胜时停止工作，并抑制后续消息 |
| 进度重置每一个截止时间 | 挂起的工作永远存活 | 保留一个单独的绝对最大超时 |
| 新的 RPC id 被当成去重 | 扣款、部署或删除跑了两次 | 增加一个持久的应用幂等键 |
| 键检查和效果是分开的 | 并发工作者都观察到键缺失 | 把键声明、效果记录和结果原子地提交 |
| 跨副本使用内存账本 | 重启或另一个工作者忘记先前的提交 | 使用共享的持久存储，或上游幂等 |
| 直接返回已存储的可变结果 | 调用方的修改破坏以后的重放 | 序列化已提交的结果，并返回防御性副本 |
| 键被配上改变后的参数复用 | 一个键别名了两种业务意图 | 存储并比较参数指纹 |
| 无界进度队列 | 内存随慢消费者上升 | 在上界内合并并丢弃可替换的进度 |
| 压力下丢掉最终响应 | 客户端无法知道请求结果 | 预留容量或驱逐进度，永远不要驱逐最终响应 |
| 代理缓冲 SSE | 进度成批到达，或在超时之后到达 | 关闭缓冲，并配置兼容的代理超时 |
| 假定存在 `Last-Event-ID` | 客户端从服务器不支持的状态恢复 | 用新请求重连，并重新拉取 |
| 每个客户端都立刻重连 | 恢复制造了另一次中断 | 使用带抖动、有上限的指数退避 |
| 任务确认被当成最终取消 | UI 说已停止，工作者仍在运行 | 轮询 Task，直到出现终态 |

## 与毕业项目的连接

工具生态毕业项目应当把可靠性当成可执行的证据，而不是架构图里的一段话。

要求这些产物：

- 每种传输各一份取消竞态记录；
- 每个暴露出来的变更一张重试表；
- 一份幂等键记录和一个不匹配夹具；
- 一份并发同键记录、一次重新打开检查，以及一次变更别名检查；
- 一份有界缓冲区过载结果；
- 反向代理的 SSE 头和空闲策略；
- 一份点名权威重新拉取方法的重连计划；
- 当毕业项目使用 Task 时，一份持久 Task 取消轨迹。

本地进程里一次绿色请求只能证明快乐路径。当丢失的响应、迟到的取消、慢消费者和重连羊群都有确定性结果时，毕业项目才算可以上生产。

## 关键术语

| 术语 | 含义 |
|------|---------|
| 请求取消 | 放弃一个在途的 MCP 请求 |
| 取消竞态 | 终态完成与取消事件之间的竞争 |
| 空闲超时 | 自上次有用请求活动以来的限制 |
| 最大超时 | 从请求开始起的绝对限制，不受进度影响 |
| 幂等键 | 对一次业务意图去重的应用标识符 |
| 原子账本 | 把键声明、效果记录和结果作为一体提交的持久边界 |
| 背压 | 生产者快过消费者时施加的控制 |
| 进度合并 | 用更新的权威值替换较旧的进度 |
| 重新拉取 | 流出现缺口之后再次读取当前状态 |
| 抖动 | 故意的变化，把重试摊开到时间上 |
