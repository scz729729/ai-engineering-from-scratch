# MCP 注册表供应链：准入、漂移与回滚

> 中文译文。代码、命令和标识符保持英文。若与原文不一致，以同目录 docs/en.md 为准。

> 注册表条目告诉你发布者声明了什么。生产准入证明的是你取到了什么、观察到了什么、批准了什么，以及你可以安全恢复什么。

**Type:** 动手做
**Languages:** Python
**Prerequisites:** Phase 13 · 17（网关与注册表）、Phase 13 · 18（生产环境认证）
**Time:** ~90 分钟

## 学习目标

- 把注册表发布、包溯源、运行时发现和本地批准分开。
- 验证 MCP（模型上下文协议）服务器的命名空间，而不信任它自己记录里面的名字。
- 把不可变的发布、执行来源、溯源和实时描述符证据都固定住。
- 在准入之后检测注册表状态变化和运行时漂移。
- 把路由回滚到先前已准入的版本，而不改写历史。
- 维护一份篡改可检测的准入账本，解释每一项决定。

## 问题

你在注册表里找到 `com.example/inventory`。描述看起来对。包也在。服务器会应答 `server/discover`。

这不是一个事实。它是一串来自不同权威的事实：

1. 某个已通过命名空间认证的发布者提交了一条记录。
2. 某个包注册表提供了一份带特定身份和摘要的制品。
3. 某个正在运行的端点报告了协议版本、能力、工具，以及诊断用的服务器信息。
4. 你的组织判定：这一精确组合是被允许的。

把这些事实塌缩成「它在注册表里，所以信任它」，就会留下一块供应链盲区。一次有效的发布仍然可能被标为 deprecated。如果你不把摘要固定住，包标签可能指向一份意料之外的制品。服务器可能在评审之后再加一个破坏性工具。一次回滚可能悄悄选中一个从未准入的版本。

修法是一个在每个边界都带证据的准入控制器。

## 注册表是索引，不是你的批准系统

官方 MCP 注册表存放服务器元数据。它的 `server.json` 记录为一个服务器版本命名，并声明一个或多个包或远程端点。发布规则额外加上命名空间认证、包所有权检查、受限注册表规则，以及一处狭窄的发布者元数据位置。

这些控制回答的是发布问题。你的生产策略仍然要回答部署问题：

| 边界 | 问题 | 证据所有者 |
|---|---|---|
| 命名空间 | 发布者是否被允许使用这个名字？ | 注册表认证，加上你已验证的命名空间输入 |
| 记录 | 发布者对这个版本声明了什么？ | 不可变的 `server.json` 摘要 |
| 执行来源 | 哪个包或远程端点将会执行？ | 已声明的来源字段、已验证的所有权结果、传输方式，以及受信任的摘要 |
| 运行时 | 端点现在暴露了什么？ | `server/discover` 和工具描述符 |
| 准入 | 你的策略是否批准了这一精确集合？ | 本地固定项和账本条目 |
| 运维 | 它是否仍然安全，以及什么可以替换它？ | 漂移检查、状态同步、健康状况和回滚路由 |

注册表 schema 版本和 MCP 协议版本是彼此独立的。一条记录可以用已发布的 `2025-12-11` 服务器 schema，而活着的服务器支持的是 MCP `2026-07-28`。绝不要从其中一个推断另一个。

```figure
mcp-registry-admission
```

## 一次准入决定里的七项控制

### 1. 命名空间验证

官方注册表的名字使用经过认证的命名空间。一个已验证的域名可以映射到反转后的域名前缀。例如，掌握 `example.com` 就可以确立 `com.example/*`。

不要接受字符串前缀检查：

```python
server_name.startswith("com.example")
```

那也会放行 `com.exampleevil/tool`。在 `/` 处拆开名字，要求 slug 非空，并且精确比较命名空间那一段。更重要的是，把已验证的命名空间从认证结果传进准入。不要从未受信任的记录里推导出信任。

由 GitHub 支撑的命名空间和由域名支撑的命名空间走不同的认证路径。把任一路径都规范化成同一个准入输入：那条精确的、已验证的命名空间字符串。

### 2. 溯源联结

对一条包记录，声明和取回的制品必须在这些显式字段上联结：

- 包注册表类型
- 包标识符
- 包版本
- 已验证的所有权结果
- 已下载制品的摘要

还要校验所声明的包传输方式。只有远程端点的记录是有效的，不能因为缺少包就拒绝它。对远程来源，把所声明的 URL 和传输类型，联结到独立验证过的端点所有权，以及受信任连接或部署证据的一份摘要。

本课代码两种来源都支持，并把所选来源连同注册表来源、服务器名、注册表版本、记录摘要和证据摘要一起做哈希。得到的溯源摘要是指向整套证据的一个紧凑指针。它不能代替把证据本身留存下来。

绝不要接受一份只由你正在验证的那个制品提供的摘要。要么在受信任的获取边界上计算它，要么从某个包服务接收它，并且要校验那个服务的验证结果。

### 3. 固定的是决定，不只是版本

注册表版本是唯一的发布标识符。已发布的元数据不可变。记录一改，就必须有一个新版本。推荐使用语义化版本，但注册表并不要求它，也不接受版本范围。

因此 `^1.4` 不是准入固定项。「latest」也不是。一份有用的固定项包含：

```json
{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}
```

把好几层都固定住，你才能认出是哪一个边界变了。同一个注册表版本下记录摘要变了，这是注册表完整性失败。同一个包坐标或同一处远程部署下来源摘要变了，这是执行来源的完整性失败。工具集摘要变了，就是运行时漂移。

### 4. 实时漂移检测

准入应当观察真正会接到流量的那台服务器。调用 `server/discover`，经由你的受信任路径列出或以其他方式取得暴露出来的工具描述符，并核实：

- `supportedVersions` 里有 `2026-07-28`
- 本地要求的能力全都在
- 每个工具描述符都有所要求的身份和 schema 表面
- 后续检查时，规范化后的描述符摘要与已准入的固定项一致

可选结果 `_meta["io.modelcontextprotocol/serverInfo"]` 的值，是服务器自报的展示、日志和调试上下文。把它记成诊断证据，但绝不要用它来确立命名空间、包所有权、端点所有权、准入，或任何其他安全决策。`_meta` 之外直接的 `serverInfo` 别名不是契约字段，不应当被提升成诊断证据。

只规范化那些顺序没有意义的字段。示例在哈希之前按稳定的名字对工具列表排序，因此无害的列表顺序变化不会造成漂移。它不会丢掉描述符字段。新工具、改过的 schema、改过的描述，或新的注解，都会改变固定项。

示例把畸形描述符和任何描述符摘要变化都当成漂移，隔离该固定项，撤掉它的活跃路由，并禁止把该版本当作回滚目标。生产策略可以规定：编辑性改动只能走一次新的评审，因为描述会影响模型怎么选工具。「外观性」元数据可以改变智能体行为。

### 5. 注册表状态是活的状态

注册表 API 在每条服务器记录旁边附上一个响应级的 `_meta` 对象。注册表管理的字段位于 `_meta["io.modelcontextprotocol.registry/official"]` 之下。把响应的 `_meta` 对象传给准入，并读取 `_meta["io.modelcontextprotocol.registry/official"].status`。直接的 `_meta.status` 值不是官方的线上形态。不要把响应元数据和发布记录自己的 `_meta` 搞混。状态可以是：

- `active`：默认会被返回，并且有资格做本地准入
- `deprecated`：仍可被发现，但带警告，不再是安全的自动选择
- `deleted`：默认隐藏，但它的历史记录仍可通过已删除视图或增量视图拿到

准入之后要同步状态。如果一个 active 版本变成 deprecated 或 deleted，隔离它的固定项，并停止把新工作路由过去。证据留着。从默认列表里消失，并不等于允许你抹掉审计轨迹。

发布者提供的自定义元数据，只属于发布记录里的 `_meta.io.modelcontextprotocol.registry/publisher-provided`。注册表管理的响应元数据是另一回事。不要让发布者给自己设置官方状态。

### 6. 回滚意味着恢复路由

回滚不会去改一份不可变的发布。回滚是选出一个先前已准入、当前仍合格的固定项，并改掉活跃路由。

安全的目标必须：

1. 有一条已完成的准入记录。
2. 在你的策略下，注册表状态仍然是 active。
3. 没有被运行时或安全证据隔离。
4. 仍然解析到已固定的包和实时描述符集合。
5. 通过当前的健康检查。

示例只盯住前三个条件。真正的调和器应当在激活之前重新获取包，并重新检查实时端点。

### 7. 追加一条准入账本

准入数据库说的是什么正处于活跃。账本解释的是为什么。

每条示例条目都包含序号、时间、事件、服务器、版本、结果、原因、证据、前一条目的哈希，以及它自己的哈希。改掉一条较旧的结果，会破坏该条目以及之后每一环的校验。

这是篡改可检测，不是魔法般的防篡改。把周期性的账本头锚定到另一个信任域，例如已签名的发布元数据，或一次写入存储。限制谁可以追加。授权令牌、包凭据、工具参数和私有端点数据都不要放进证据。

## 动手做

可运行的控制器在 `code/main.py`。它只用 Python 标准库。

从这段有限的演示开始：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
```

演示做五件事：

1. 准入 `1.0.0`，其命名空间、包溯源、协议、能力和工具都匹配。
2. 准入 `1.1.0`，并让它成为活跃版本。
3. 在运行时观察到一个意料之外的删除工具。
4. 观察到 `1.1.0` 的注册表状态变成 `deprecated`。
5. 把路由恢复到仍然处于已准入状态的 `1.0.0` 固定项。

预期形状：

```json
{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}
```

按这个顺序读实现：

1. `namespace_for_domain()` 和 `namespace_matches()` 确立精确的命名权威。
2. `digest()` 和 `normalized_tools()` 产生确定性证据。
3. `RegistryAdmissionController.admit()` 把发布、溯源、运行时和策略联结起来。
4. `check_live()` 把一次新观察和固定项比较。
5. `observe_registry_status()` 隔离注册表状态发生了变化的版本。
6. `rollback()` 只激活先前已准入且仍合格的目标。
7. `AdmissionLedger.verify()` 检测已记录历史被改动。

## 使用

把控制器放在发现和路由之间：

```text
Registry sync -> artifact verifier -> live discovery -> admission controller -> route table
                                               |                 |
                                               v                 v
                                          evidence store    admission ledger
```

这些工作用彼此分开的身份。注册表同步工作者需要对元数据的读权限。制品校验器需要获取包的权限。路由调和器需要激活已批准固定项的权限。它们谁也不需要全部凭据。

把推出状态写清楚。「已批准」表示证据通过了策略。「活跃」表示路由当前选中了它。「已隔离」表示它不能再接收新工作。「已被取代」表示另一个已准入版本正处于活跃。不要用一个布尔值编码这四种含义。

在 `tools/list` 里暴露一台服务器之前，先跑准入。否则客户端会在发布和策略评估之间的空档里发现某个工具。

## 交互实验

你将一次只看一个边界失败。

### 实验 A：命名空间碰撞

在代码目录里打开一个 Python shell：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/code
python3 -q
```

然后运行：

```python
from main import namespace_matches
namespace_matches("com.example/inventory", "com.example")
namespace_matches("com.exampleevil/inventory", "com.example")
```

第一个结果是 `True`；第二个是 `False`。在本地把精确比较换成 `startswith`，观察第二个名字为什么越过了边界。继续之前，把精确比较改回去。

### 实验 B：描述符漂移

```python
from main import *
times = iter(f"2026-08-21T12:00:{n:02d}+00:00" for n in range(10))
c = RegistryAdmissionController(clock=lambda: next(times))
meta = {OFFICIAL_META_KEY: {"status": "active"}}
c.admit(sample_record("1.0.0"), meta, "com.example", evidence_for("1.0.0"), sample_live("1.0.0"))
c.check_live("com.example/inventory", "1.0.0", sample_live("1.0.0", True))
```

查看原因和路由状态。包和注册表记录都没变。变的是运行时的工具表面，所以控制器隔离并停用了这个固定项。这就是为什么供应链控制在安装之后还得继续。

### 实验 C：状态与回滚

准入 `1.1.0`，把它标成 deprecated，然后两个回滚目标都试一次：

```python
c.admit(sample_record("1.1.0"), meta, "com.example", evidence_for("1.1.0"), sample_live("1.1.0"))
c.observe_registry_status("com.example/inventory", "1.1.0", "deprecated")
c.rollback("com.example/inventory", "1.1.0", "unsafe retry")
c.rollback("com.example/inventory", "1.0.0", "restore known release")
c.ledger.verify()
```

被隔离的目标会被拒绝。更早的那个活跃固定项会被接受。账本仍然有效。

## 练习实验

给控制器加上一道双人批准门。

要求：

- 把批准存成已签名的证据引用，而不是固定项里可变的名字。
- 如果工具集里有一个带 `destructiveHint: true` 的工具，就要求两个不同的评审者身份。
- 拒绝重复的评审者身份。
- 批准不完整时，在账本里保留最初的那次准入尝试。
- 为零次、一次、重复，以及两次不同的批准补上测试。
- 不要记录签名、凭据，或完整的私有工具参数。

成功的标准是：在两个身份都批准了精确的记录摘要、包摘要和工具集摘要之前，破坏性工具不能变成活跃。

## 验证

跑演示和那套确定性测试：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

验证应当证明：

- 精确的命名空间边界会拒绝形似的前缀
- 只有官方的、带命名空间的注册表状态才能让一个版本合格
- 未验证或不匹配的包证据和远程证据会被拒绝
- 发布者元数据不能冒充注册表管理的元数据
- 工具顺序会被规范化，同时不隐藏描述符变化
- 畸形的包结构和工具结构会安全地拒绝
- `serverInfo` 保持为诊断用途，从不提供准入权威
- 描述符漂移会隔离、停用，并阻止回滚到该固定项
- 状态变化会隔离活跃的固定项
- 回滚不能选择已隔离或未知的版本
- 账本篡改会被检测出来

## 生产失败模式

| 失败 | 为何发生 | 所需响应 |
|---|---|---|
| 名字看起来合法，但命名空间从未被认证 | 策略信任了记录文本 | 拒绝，直到一个受信任的命名空间校验器给出精确前缀 |
| 同一个包坐标返回了新的字节 | 上游可变，或分发已被攻破 | 停止激活，两份摘要都留着，调查获取边界 |
| 「Latest」未经评审就变了 | 浮动选择逃出了固定项 | 只解析精确的已准入版本和摘要 |
| 批准之后出现了新工具 | 运行时漂移，或部署的是另一份 | 隔离路由，并捕获一份新的描述符观察 |
| 已弃用的版本仍处于活跃 | 状态同步缺失或迟到 | 按计划调和状态，并且在激活之前再调和一次 |
| 已删除的记录从默认同步里消失 | 客户端只请求了 active 记录 | 使用增量或感知删除的调和，并保留本地历史 |
| 回滚目标从未被准入 | 路由控制和批准状态是断开的 | 拒绝回滚，并对该目标跑一次新的准入 |
| 攻击者重写全部条目之后，账本在本地仍然校验通过 | 哈希链没有外部锚点 | 把已签名的账本头发布到另一个信任域 |
| 证据里含有 bearer 令牌或工具参数 | 日志把整个请求都抄了下来 | 在采集时脱敏，并且只存最小证明 |

## 运维规则

发布回答的是「这个身份能不能发布这个名字？」准入回答的是「我们会不会执行这一份精确的制品，并暴露这一份精确的行为？」把这两个决定分开，固定每一次联结，让回滚去选证据，而不是去选记忆。
