# 工具接口——为什么智能体需要结构化 I/O

> 中文译文。代码、命令和标识符保持英文。若与原文不一致，以同目录 docs/en.md 为准。

> 语言模型产出 token。程序采取行动。两者之间的鸿沟就是工具接口：一份让模型请求某个动作、由宿主执行该动作的契约。2026 年的每一种技术栈——OpenAI、Anthropic 与 Gemini 上的函数调用；MCP（模型上下文协议）的 `tools/call`；A2A 的任务部分——都是同一套四步循环的不同编码。本课命名这个循环，并展示跑通它所需的最小机制。

**Type:** 理解
**Languages:** Python（标准库，无 LLM）
**Prerequisites:** 第 11 阶段（LLM 补全 API）
**Time:** ~45 分钟

## 学习目标

- 解释为什么只能生成文本的 LLM 无法靠自身对真实世界采取行动。
- 画出四步工具调用循环（描述 → 决策 → 执行 → 观察），并指出每一步由谁负责。
- 把工具描述写成三部分：名称、JSON Schema 输入，以及一个确定性的执行器函数。
- 区分纯工具与有副作用的工具，并说明这种划分为何关系到安全。

## 问题

LLM 对下一个 token 输出一个概率分布。这就是它的全部输出面。如果你问聊天模型「Bengaluru 现在天气怎么样」，它可以写出一句看似合理的话，但无法拨通天气 API。这句话可能碰巧正确，也可能已经过时三天。

弥合这一鸿沟，正是工具接口的目的。宿主程序——你的智能体运行时、Claude Desktop、ChatGPT、Cursor，或一段自定义脚本——向模型公布一份可调用工具列表。当模型判定需要某个动作时，它发出一份结构化载荷，指名工具及其参数。宿主解析该载荷，真正运行工具，再把结果喂回去。循环持续，直到模型判定不再需要调用。

这份契约的第一版于 2023 年 6 月以 OpenAI 的 "functions" 参数发布。Anthropic 随后在 Claude 2.1 中跟进了 `tool_use` 块。几个月后 Gemini 加入了 `functionDeclarations`。如今每个提供商都暴露同一形态：输入一份以 JSON Schema 类型化的工具列表，输出一份 JSON 载荷形式的工具调用。Model Context Protocol（模型上下文协议，2024 年 11 月）把这份契约推广成一份工具注册表，服务每一个模型。A2A（2026 年 4 月，v1.0）把同一原语叠加上去，用于智能体到智能体的委托。

四步循环是这一切底下的不变量。第 13 阶段的其余内容都是对它的展开。

## 概念

### 第一步：描述

宿主用三个字段声明每个工具。

- **名称。** 稳定、机器可读的标识符。`get_weather`，而不是 "weather thing"。
- **描述。** 一段自然语言简介。"Use when the user asks about current conditions for a specific city. Do not use for historical data."
- **输入 schema。** 一个 JSON Schema 对象（draft 2020-12），描述该工具的参数。

模型收到这份列表。现代提供商用各自的模板把这些声明序列化进系统提示，因此作为调用方，你只需要处理结构化形式。

### 第二步：决策

给定用户消息和可用工具，模型在三种行为中选择一种。

1. **直接回答**，用文本。不发起工具调用。
2. **调用一个或多个工具。** 发出结构化调用对象。在 `parallel_tool_calls: true` 下（OpenAI 与 Gemini 默认开启，Anthropic 为选择启用），模型可以在一轮中发出多次调用。
3. **拒绝。** 严格模式的结构化输出可以产生一个带类型的 `refusal` 块，而不是一次调用。

一次工具调用载荷有三个稳定字段：调用 `id`、工具 `name`，以及一个 JSON `arguments` 对象。id 的存在是为了让宿主把后续结果与这次具体调用关联起来；当并行调用乱序返回时，这一点很重要。

### 第三步：执行

宿主收到调用，对照已声明的 schema 校验参数，然后运行执行器。参数无效意味着模型幻觉出一个字段，或用错了类型——这在较弱的模型上是非常常见的失败模式。生产环境的宿主在参数无效时做三件事之一：快速失败并把错误呈现给模型，用受约束解析器修复 JSON，或把校验错误写进提示后重试模型。

执行器本身就是普通代码。Python、TypeScript、一条 shell 命令、一次数据库查询。它产出一个结果，通常是字符串，但也可以是任意 JSON 值，或一个结构化内容块（MCP 中的文本、图像或资源引用）。结果必须可序列化。

### 第四步：观察

宿主把工具结果追加到对话中（作为带有匹配 `id` 的 `tool` 角色消息），并再次调用模型。模型此时在上下文中拥有工具输出，可以给出最终回答，或请求更多调用。如此继续，直到模型停止发出调用，或宿主达到迭代次数的安全上限。

### 信任划分

工具有两种与安全相关的形态。

- **纯工具。** 只读、确定性、无副作用。`get_weather`、`search_docs`、`get_current_time`。可以投机性地调用。
- **有后果的工具。** 改变状态、花钱、接触用户数据。`send_email`、`delete_file`、`execute_trade`。必须设闸。

Meta 在 2026 年针对智能体安全提出的 "Rule of Two" 说，单轮至多只能组合以下三者中的两个：不可信输入、敏感数据、有后果的动作。工具接口正是你强制执行该规则的地方——通过拒绝调用、要求用户确认，或提升作用域。完整安全章节见第 13 阶段 · 15，智能体级权限策略见第 14 阶段 · 09。

### 循环住在哪里

| 上下文 | 谁来描述 | 谁来决策 | 谁来执行 |
|---------|---------------|-------------|--------------|
| 单轮函数调用（OpenAI/Anthropic/Gemini） | 应用开发者 | LLM | 应用开发者 |
| MCP | MCP 服务端 | 经由 MCP 客户端的 LLM | MCP 服务端 |
| A2A | Agent Card 发布者 | 发起调用的智能体 | 被调用的智能体 |
| Web 浏览器（函数调用智能体） | 浏览器扩展 / WebMCP | LLM | 浏览器运行时 |

到处都是同样的四步。列名会变；结构不变。

### 为什么不直接提示模型输出 JSON？

「让模型用 JSON 回复」是函数调用出现之前的做法。它在前沿模型上大约有 5% 到 15% 的失败率，在更小的模型上失败更多。失败模式包括缺少花括号、尾随逗号、幻觉字段和错误类型。于是你还需要一次 JSON 修复、一次重试，或一个受约束解码器。

原生函数调用更好，原因有三。第一，提供商以确切的调用形态对模型做端到端训练，因此在严格模式下合法 JSON 的比率升到 98% 到 99%。第二，调用载荷位于自己的协议槽位，而不是自由文本里——因此工具调用绝不会泄漏进用户可见的回复。第三，提供商用受约束解码强制 schema 合规（OpenAI 的严格模式、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`）。输出保证能通过校验。

### 熔断器

当模型停止发出调用，或宿主达到最大轮数时，循环终止。生产环境的宿主把这个上限设在 5 到 20 轮之间。超过这个范围，你几乎肯定陷入了模型无法自行退出的循环。Claude Code 默认 20；OpenAI Assistants 默认 10；Cursor 的智能体模式默认 25。

另一种选择——无界循环——每隔大约六个月就会以「智能体一夜之间在 API 调用上花了 400 美元」的事后复盘出现。不要在没有上限的情况下交付。

第 14 阶段 · 12 深入讲错误恢复与自愈；第 17 阶段讲生产环境的速率限制。

## 用起来

`code/main.py` 在没有 LLM 的情况下运行四步循环。一个假的「决策器」函数通过对用户消息做模式匹配来模拟模型；执行器、schema 校验器和观察步骤的运行框架是真的。运行它，看完整的请求/响应编排以及可打印的中间状态，然后在后续课程里把假决策器换成任意真实提供商。

要看的地方：

- 工具注册表为每个工具保存三个字段：名称、描述、schema，以及一个执行器引用。
- 校验器是一个最小的 JSON Schema 子集（类型、required、enum、min/max），只用标准库写成。第 13 阶段 · 04 会交付更完整的版本。
- 循环把迭代次数限制在五次。生产环境的智能体恰恰需要这种熔断器。

## 交付

本课产出 `outputs/skill-tool-interface-reviewer.md`。给定一份工具定义草稿（名称 + 描述 + schema + 执行器提纲），该技能会审计它是否适合进入循环：名称是否对机器稳定，描述是否是一份完整的用法简介，schema 是否正确使用 JSON Schema 2020-12，以及纯工具与有后果工具的分类是否明确。

## 练习

1. 在 `code/main.py` 中增加第四个工具，名为 `get_stock_price(ticker)`。把它的描述写成 "Use when the user asks for a current stock price by ticker. Do not use for historical prices or market summaries." 运行该框架，确认假决策器会把提到 ticker 的查询路由到这个新工具。

2. 弄坏 schema 校验器。传入一次 `arguments` 对象缺少必填字段的调用，确认宿主在执行前拒绝它。然后再传入一次带有额外未知字段的调用。做出决定：宿主应该拒绝还是忽略？用一个安全论证来说明你的选择。

3. 把运行框架中的每个工具分类为纯工具或有后果的工具。给需要它的注册表条目加上 `consequential: true` 标志，并修改循环，使得每当选中一个有后果的工具时打印一行 "would confirm with user"。这就是每个生产环境宿主都需要的确认闸门的形态。

4. 在纸上画出四步循环，并用上面的提供商列表格填上你最喜欢的客户端（Claude Desktop、Cursor、ChatGPT，或自定义技术栈）。与第 13 阶段 · 06 中 MCP 专用变体交叉对照。

5. 从头到尾阅读 OpenAI 的函数调用指南。找出一个出现在请求中、但并不在这里呈现的四步循环里的字段。解释它增加了什么，以及为什么它是便利而非必要。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|----------------|------------------------|
| 工具 | 「模型可以调用的一个东西」 | 名称 + 以 JSON Schema 类型化的输入 + 执行器函数，三者合一 |
| 函数调用 | 「原生工具使用」 | 提供商层面的 API 支持，用于发出结构化工具调用，而不是散文 |
| 工具调用 | 「模型请求采取行动」 | 模型发出的 JSON 载荷，含 `id`、`name`、`arguments` |
| 工具结果 | 「工具返回了什么」 | 执行器的输出，包在一条带有匹配 id 的 `tool` 角色消息里 |
| 并行工具调用 | 「一次很多调用」 | 模型一轮中的多个调用对象，彼此独立，并可按 id 排序 |
| 严格模式 | 「保证是 JSON」 | 受约束解码，迫使模型输出对照已声明 schema 通过校验 |
| 纯工具 | 「只读工具」 | 无副作用；可以安全地重新运行 |
| 有后果的工具 | 「动作工具」 | 改变外部状态；需要闸门、审计或用户确认 |
| 四步循环 | 「工具调用周期」 | 描述 → 决策 → 执行 → 观察 |
| 宿主 | 「智能体运行时」 | 持有工具注册表、调用模型并运行执行器的程序 |
